# 第一阶段 落地链路改造清单

> 来源：「新增页面配置 → 菜单 → 路由 → 文件 → 权限」落地链路审查结论
> 编写日期：2026-10-30
> 状态：待开发

---

## 0. 前提（用户确认，覆盖审查报告中的旧建议）

1. `nav_menu` 中一条菜单是**多个域共用同一条记录**，域只通过 `sys_domain_menu` 加关联（`custom_parent_id` / `custom_level` 表达域内层级）。
2. 页面生成器新建的菜单**只关联默认（当前）域**，其他域由人工在「域管理」里开启——这是长期策略，不改。
3. 因此 **作废** 上一轮的旧建议：不给 `page_definition` 加 `domain_id`、菜单 key 不带域。
4. 新原则：
   - 清理 / 取消发布前，按 `sys_domain_menu` **引用计数**决定能否物理删除菜单；仍被其他域引用时**只撤本域关联**。
   - `nav_menu` 需能区分「生成器创建」与「人工创建」。
   - `bind_existing` 绑定与还原 path 前，先比对当前值是否由本流程写入。

## 0.1 Flyway 版本基线

- 当前 `material-system-server/src/main/resources/db/migration/` 最高版本：**V28**（`V28__ai_model_config.sql`）。
- 本清单新增脚本从 **V29** 起编：**V29（A 批）→ V30（B 批）→ V31（C 批）**，D 批无数据库变更。
- 所有脚本必须幂等（`information_schema` 判断 + `PREPARE` 写法，参照 V25 风格）；**严禁修改 V1~V28 任何已执行脚本**。
- V26 / V27 是页面生成器此前自动产出的业务表脚本（`dynamic_ren-wu-lie-biao` 系列），属历史遗留证据，不在本阶段处理，但 D 批完成后此类脚本不应再新增。

## A 批：止血

**目标**：不再新增「配置改了但菜单清理按旧事实推算」的断点；bind 不抢占别人的菜单；还原 path 不误伤人工改动；同 pageKey 的二次删除不再 500。

### A-1 锁定已发布配置的关键字段

- **文件与方法**：[PageDefinitionServiceImpl.java](file:///Users/xiongdongying/ai_project/yph-react/material-system-server/src/main/java/com/material/server/service/impl/PageDefinitionServiceImpl.java) `saveSchema` L57-L107（字段覆盖发生在 L93-L101）。
- **改法**：
  - `saveSchema` 中，`existingId != null` 且 `entity.status == "published"` 时，比对 DTO 与库内实体的 5 个关键字段：`pageKey`、`menuLinkMode`、`parentMenuId`、`bindMenuId`、`tableName`。
  - 任一字段发生变化 → 抛 `BusinessException("页面已发布，请先取消发布再修改挂载方式/页面标识/数据表")`；仅允许改 `pageName`、`apiPrefix`、字段/列配置等 schema 内容。
  - 前端 [PageGeneratorWizard.tsx](file:///Users/xiongdongying/ai_project/yph-react/react-system/src/pages/generator/PageGeneratorWizard.tsx) 在编辑已发布配置时把上述字段对应的表单项置为 disabled（向导第 1 步 pageKey、菜单挂载区块；位置在 L735-L760 组装 payload 之前做防御即可，后端校验为准）。
- **数据库变更**：无。
- **手工验证**：
  1. 发布一个 new_child 页面 → 编辑改父菜单 → 保存应报错且菜单不变。
  2. 取消发布 → 改父菜单 → 保存成功 → 重新发布 → 菜单出现在新父菜单下。
- **风险与回滚**：低风险；个别历史已发布配置若需改挂载，必须先取消发布（符合预期）。回滚 = 还原后端方法即可。

### A-2 bind_existing 绑定占用校验

- **文件与方法**：`syncMenu` bind 分支 [PageDefinitionServiceImpl.java](file:///Users/xiongdongying/ai_project/yph-react/material-system-server/src/main/java/com/material/server/service/impl/PageDefinitionServiceImpl.java#L324-L341) L324-L341。
- **改法**：
  - 绑定前校验一：`page_definition` 中不存在另一条 `status='published' AND bind_menu_id={该菜单} AND id != {当前id} AND deleted=0` 的记录，否则抛 `BusinessException("该菜单已被页面配置「{pageName}」绑定")`。
  - 绑定前校验二：`exist.getPath()` 若已等于 `/dynamic/{其他pageKey}`（前缀匹配 `/dynamic/` 且不等于本配置的 pageKey），同样拒绝——防止覆盖一个已被生成器接管、但绑定记录已删除的菜单。
  - 校验三（配合 C 批的长期策略）：bind 目标菜单若尚未关联当前域，不自动补域关联，仅提示「该菜单未在当前域开启，请先在域管理中开启」。
- **数据库变更**：无。
- **手工验证**：建两个页面配置同时绑同一菜单 → 第二个发布报占用错误；把第一个取消发布 → 第二个可发布。
- **风险与回滚**：可能暴露存量「一菜多绑」脏数据（发布报错即发现）；回滚 = 去掉校验逻辑。

### A-3 还原 path 前先比对「是否本流程写入」

- **文件与方法**：`restoreBindMenuPath` [PageDefinitionServiceImpl.java](file:///Users/xiongdongying/ai_project/yph-react/material-system-server/src/main/java/com/material/server/service/impl/PageDefinitionServiceImpl.java#L256-L271) L256-L271。
- **改法**：还原前判断 `menu.getPath()` 是否等于 `/dynamic/{entity.pageKey}`：
  - 相等 → 写回 `originalMenuPath`（现有逻辑）；
  - 不相等 → 说明管理员已人工改过路径，**跳过还原**，仅 `log.warn` 并保留当前值；
  - `originalMenuPath` 为 null（旧数据）时不再把 path 置空，改为仅记录日志（置空会让菜单 404，比指向旧动态页更糟）。
- **数据库变更**：无。
- **手工验证**：bind 发布 → 在菜单管理手工把该菜单 path 改为 `/xxx` → 删除页面配置 → 菜单 path 仍为 `/xxx` 不被还原。
- **风险与回滚**：低风险。回滚 = 还原方法。

### A-4 修复 `uk_page_key_del` 导致的二次删除 500

- **文件与方法**：索引由 [V22__fix_softdelete_unique_indexes.sql](file:///Users/xiongdongying/ai_project/yph-react/material-system-server/src/main/resources/db/migration/V22__fix_softdelete_unique_indexes.sql#L52-L56) L52-L56 建立（`page_key, deleted`）；实体逻辑删注解在 [PageDefinition.java](file:///Users/xiongdongying/ai_project/yph-react/material-system-server/src/main/java/com/material/server/entity/PageDefinition.java#L51) L51 附近（`@TableLogic deleted`）。
- **问题**：`deleted` 只有 0/1 两个值，同 pageKey 删除 → 重建 → 再删除时，两行 `(pageKey, deleted=1)` 冲突报唯一键错误。
- **改法（新脚本 V29__page_definition_fix_redelete_unique.sql）**：
  1. `page_definition.deleted` 由 `TINYINT` 改为 `BIGINT NOT NULL DEFAULT 0`（幂等：`information_schema.COLUMNS` 判断 `DATA_TYPE`）。
  2. 存量已删除行回填：`UPDATE page_definition SET deleted = id WHERE deleted = 1`（天然幂等，第二次执行为空集）。
  3. 实体 `@TableLogic(value = "0", delval = "id")`——删除时 `deleted` 置为行 id，保证 `(page_key, deleted)` 永不冲突；唯一索引本身不动。
- **数据库变更**：✅ V29。
- **手工验证**：同一 pageKey「发布→删除→重建→再删除」全流程不报错；`flyway_schema_history` 出现 V29 且 `success=1`。
- **风险与回滚**：`delval="id"` 是 MyBatis-Plus 标准用法，但需回归所有按 `deleted=0` 手写 SQL 的地方（本项目查询均走 MyBatis-Plus 自动拼 `deleted=0`，低风险）。回滚 = 还原实体注解 + 把列改回 TINYINT（需确认无大于 1 的值）。

## B 批：发布快照

**目标**：发布时把「本次实际创建/绑定了哪条菜单、当时的原 path / 原父级」落成独立快照；此后清理、改绑、还原一律以快照为准，不再从「当前配置」推算「历史事实」。这是 C 批的数据基础。

### B-1 新建快照表 `page_menu_link`（V30）

- **改法（新脚本 V30__page_menu_link_snapshot.sql）**：

| 列 | 类型 | 说明 |
|---|---|---|
| id | BIGINT AUTO_INCREMENT PK | |
| page_definition_id | BIGINT NOT NULL | 关联 page_definition |
| page_key | VARCHAR(100) NOT NULL | 冗余，便于排查 |
| menu_id | BIGINT NOT NULL | 本次发布实际写入的菜单 |
| link_action | VARCHAR(20) NOT NULL | `created`（新建子菜单）/ `bound`（绑定改写 path） |
| original_path | VARCHAR(200) NULL | bound 时记录发布前 path |
| original_parent_id | BIGINT NULL | created 时记录发布时父菜单 |
| original_level / original_sort | INT NULL | created 时记录初始层级/排序 |
| domain_id | BIGINT NULL | 本次发布同步到的域 |
| publish_time | DATETIME | 本次发布时间 |
| active | TINYINT NOT NULL DEFAULT 1 | 最近一次发布为 1，历史快照置 0 |
| created_time / updated_time / deleted | 常规 | deleted 走逻辑删 |

  - 幂等写法：`CREATE TABLE IF NOT EXISTS`；普通索引 `(page_definition_id, active)`、`(menu_id)` 即可，**不加唯一索引**。
  - 存量数据回填（幂等，`INSERT ... SELECT ... WHERE NOT EXISTS`）：对已 `published` 且 `bind_menu_id IS NOT NULL` 的 `page_definition`，按 `original_menu_path`（V23 引入的列）生成 `link_action='bound'` 的快照；对 published 的 new_child 配置，按 `key='dynamic-'+page_key` 反查 `nav_menu` 生成 `link_action='created'` 快照（查不到菜单的跳过并留日志，属存量孤儿，C 批验收时人工处理）。

### B-2 publish 写快照

- **文件与方法**：`publish` L109-L156、`syncMenu` L315-L388（[PageDefinitionServiceImpl.java](file:///Users/xiongdongying/ai_project/yph-react/material-system-server/src/main/java/com/material/server/service/impl/PageDefinitionServiceImpl.java)）。
- **改法**：
  - `publish` 开始（同一事务内）先把该 `page_definition_id` 的既有快照 `active` 全部置 0。
  - `syncMenu` bind 分支（L324-L341）：改 path 前从 `exist` 读出原 `path/parentId/level/sort` 写入快照（`link_action='bound'`）；`original_menu_path` 列保留不动（向后兼容，新逻辑不再读它）。
  - new_child 分支（L356-L378）：无论「新建」还是「命中已有菜单只更新 label/path」，都把最终 `menuId` 写入快照（`link_action='created'`，记录当时的 `parentId/level/sort` 与 `domainId`）。
  - 新增 `PageMenuLink` entity / mapper / 在 `PageDefinitionServiceImpl` 注入（参照现有 `SysDomainMenu` 模式，无 Service 层，直接 Mapper）。
- **数据库变更**：✅ 依赖 V30。
- **手工验证**：发布一个 new_child → 快照表出现 `created` 行且 `menu_id` 等于新菜单；改字段重新发布 → 旧快照 `active=0`、新快照 `active=1`；bind 发布 → 快照 `original_path` 等于绑定前菜单的 path。
- **风险与回滚**：快照只增不改业务路径，失败会被 `@Transactional` 整体回滚。回滚 = 去掉写快照调用（表可保留）。

### B-3 清理改读快照

- **文件与方法**：`cleanupMenu` L230-L250、`restoreBindMenuPath` L256-L271。
- **改法**：
  - `cleanupMenu` 不再用 `entity.getMenuLinkMode()` 分支；改为读 `active=1` 的快照：无快照 → 按现状 warn 跳过；`created` → 走 C 批的引用计数删除（B 批先行阶段暂走现有 `cascadeDeleteMenu`，C 批切换）；`bound` → 用快照的 `menu_id + original_path` 还原，且沿用 A-3 的 path 比对。
  - `unpublish`（L178-L202）清理成功后把快照 `active` 置 0；`removeById`（L204-L223）清理成功后逻辑删快照。
- **数据库变更**：无（复用 V30 表）。
- **手工验证**：发布（new_child）→ 保存时改配置为 bind_existing（A-1 拦截，需先取消发布；此用例改走「取消发布」验证：取消发布仍正确删除 `dynamic-` 子菜单）；bind 发布后删除配置 → 菜单 path 还原为快照中的 `original_path`。
- **风险与回滚**：若快照缺失（B-1 回填漏掉的存量），行为退化为「跳过清理 + warn」，比误删安全。回滚 = 恢复按 entity 推算的旧逻辑。

## C 批：共享菜单引用计数删除

**目标**：落实用户确认的共享模型——菜单多域共用一条 `nav_menu`；取消发布/删除只撤**本域**关联；仅当菜单不再被任何域引用、且确系生成器创建时才物理（逻辑）删除；人工创建的菜单永不删。

### C-1 `nav_menu` 加来源标记（V31）

- **改法（新脚本 V31__nav_menu_add_menu_source.sql）**：
  - 幂等加列：`menu_source VARCHAR(20) NOT NULL DEFAULT 'manual' COMMENT 'manual-人工创建 generator-页面生成器创建'`。
  - 回填：`UPDATE nav_menu SET menu_source='generator' WHERE \`key\` LIKE 'dynamic-%'`（生成器菜单 key 有固定前缀，见 `syncMenu` L350；语句幂等可重复执行）。
  - 实体 [NavMenu.java](file:///Users/xiongdongying/ai_project/yph-react/material-system-server/src/main/java/com/material/server/entity/NavMenu.java) 加 `menuSource` 字段；`syncMenu` 新建子菜单处（L364-L375）显式 `setMenuSource("generator")`。
- **数据库变更**：✅ V31。
- **注意**：`nav_menu` 其余缺失列（`visible/component/perms/menu_category` 等只存在于 `init/` 的问题，审查问题 15）**不在本阶段**，另立迁移处理，避免本批次膨胀。

### C-2 引用计数删除 + 只撤本域

- **文件与方法**：`unpublish` L178-L202、`removeById` L204-L223、`cleanupMenu` L230-L250、`cascadeDeleteMenu` L277-L290、`syncDomainMenu` L393-L405；前端 [PageGenerator.tsx](file:///Users/xiongdongying/ai_project/yph-react/react-system/src/pages/generator/PageGenerator.tsx) `handleUnpublish` L214-L230、`handleDelete` L138-L160。
- **改法**：
  1. **接口变更**：`unpublish` 增加 `domainId` 参数（前端像 publish 一样从 `localStorage.currentDomainId` 取数传入，参照 [PageGeneratorWizard.tsx](file:///Users/xiongdongying/ai_project/yph-react/react-system/src/pages/generator/PageGeneratorWizard.tsx#L767-L775) L769-L770 的写法）；`removeById` 同理（`DELETE /api/page-definitions/{id}?domainId=`）。
  2. `cleanupMenu`（读 B 批快照，`created` 分支）改为：
     - 删除 `sys_domain_menu` 中 `(domain_id=当前域, menu_id=快照菜单)` 一行（只撤本域）；
     - 统计该菜单剩余 `sys_domain_menu` 行数：
       - **> 0** → 菜单仍被其他域引用：`nav_menu`、`sys_role_menu` 全部保留，结束（`sys_role_menu` 无域维度，其他域的角色仍要用）；
       - **= 0 且 `menu_source='generator'`** → 才执行级联：删 `sys_role_menu` → 逻辑删 `nav_menu`；
       - **= 0 且 `menu_source='manual'`** → 不删菜单（防御：理论上 generator 不会创建 manual 菜单的快照，留 warn 日志即可）。
  3. 物理（逻辑）删除前加**子树检查**：`nav_menu` 存在 `parent_id=menuId AND deleted=0` 的子菜单 → 抛 `BusinessException("该菜单下仍有子菜单，请先处理")`，避免产生 parent 悬空的孤儿（审查问题 17）。
  4. `bound` 分支不变（还原 path，不删任何关联——菜单本来就属于其他域/流程）。
- **数据库变更**：无（复用 V30/V31）。
- **手工验证**：
  1. 域 A 发布 → 域管理中把同一菜单开放给域 B → 回到域 A 取消发布 → 域 A 侧边栏消失、**域 B 仍可见**、`nav_menu` 行保留。
  2. 域 B 再人工移除该菜单（或回到 B 域对同一配置做发布/取消的端到端）→ 无域引用后菜单被逻辑删除、`sys_role_menu` 清空。
  3. 给该菜单手工加一个子菜单后再删除配置 → 报「仍有子菜单」。
- **风险与回滚**：核心风险是「引用计数统计时 `domainId` 传错/为空导致误删菜单」——`domainId` 为空时**直接报错拒绝**，不做兜底删除。回滚 = 恢复旧 `cascadeDeleteMenu`（但会重新产生跨域误删，回滚需评估存量）。

### C-3 权限联动收敛（随 C-2 一并改）

- **文件与方法**：`syncRoleMenuForPublisher` L407-L436。
- **改法**：new_child 发布不再「同步给所有启用角色」，改为只授 `admin` 角色 + （若存在）创建者本人所属角色；bind 分支补「复制目标菜单既有 `sys_role_menu`」的幂等插入（bind 模式此前完全不授权，发布后谁都看不见）。物理删除菜单时 `sys_role_menu` 的清理由 C-2 的级联负责，不变。
- **数据库变更**：无。
- **手工验证**：新建页发布后，用非 admin 角色账号确认默认不可见（admin 在角色管理里再分配）；bind 发布后可见性与目标菜单原有角色一致。
- **风险与回滚**：行为变更需提前知会使用者；回滚 = 恢复全量角色同步。

## 验收清单（改完后如何快速确认「孤儿菜单不再产生」)

按顺序执行以下检查（前 4 条为 SQL 巡检，可固化为脚本；后 4 条为端到端用例）：

1. **孤儿菜单巡检**：
   `SELECT m.id, m.key FROM nav_menu m WHERE m.key LIKE 'dynamic-%' AND m.deleted=0 AND NOT EXISTS (SELECT 1 FROM page_definition p WHERE p.deleted=0 AND p.status='published' AND CONCAT('dynamic-', p.page_key)=m.key);`
   —— 结果应为 0 行（每行都是一个「配置没了菜单还在」的孤儿）。
2. **域关联孤儿巡检**：`sys_domain_menu` 中 `menu_id` 指向已逻辑删 `nav_menu` 的行数应为 0；`sys_role_menu` 同理。
3. **快照一致性巡检**：`page_menu_link` 中 `active=1` 的记录，其 `menu_id` 在 `nav_menu` 必须存在且未删除；`link_action='bound'` 的快照，菜单当前 path 要么等于 `/dynamic/{page_key}`、要么等于 `original_path`（已还原），不应出现第三种值。
4. **幽灵表巡检**：`page_migration_script` 中 `deleted=0` 记录的 `page_definition_id` 必须有对应未删除的 `page_definition`；`information_schema.TABLES` 中不再新增任何 `*_detail` / `*_form` 后缀的表。
5. **端到端用例 A（编辑改挂载）**：已发布配置在 A-1 锁定下无法直接改挂载；走「取消发布→修改→重发布」后，`nav_menu` 中旧 `dynamic-` 菜单按引用计数正确处置，无残留。
6. **端到端用例 B（跨域共享）**：同一菜单开放给两个域，任一域取消发布后另一域入口不受影响（C-2 验证步骤 1）。
7. **端到端用例 C（bind 还原）**：bind 发布→删除配置→菜单 path 精确还原为快照 `original_path`；期间人工改过 path 的，删除后保持人工值（A-3）。
8. **端到端用例 D（重建同名页）**：同一 pageKey 删除→重建→再删除全流程无唯一键报错（A-4），第二次删除后巡检 1 仍为 0 行。
